Competing-Risks Churn Decision Support

Survival-analysis models + an agent that explains and recommends, grounded in real tool output.

Population-level analytics for retention/marketing decision-makers — see "Predict a customer" for the instance-level view.

Deliberate strawman: binary churn classifier

Ignores censoring and can't distinguish WHICH cause. Included on purpose, as the naive baseline the rest of this project improves on.

Kaplan-Meier: naive all-cause survival

Treats every churn reason as the same event. A useful baseline, but can't tell you WHY people are leaving.

Aalen-Johansen: cumulative incidence by cause

The correct competing-risks baseline: one curve per cause, properly accounting for the fact that a customer who churns for one reason can no longer churn for another.

Cause-specific Cox proportional hazards

Hazard ratios are associational, not causal: they describe correlation with risk in this data, not the effect of intervening on a customer.

Random Survival Forest

Nonlinear/ensemble model over the all-cause event, scored by concordance index (a ranking-quality metric, not an accuracy percentage).

Ask the agent

Try: "What's the price sensitivity churn rate within 3 months?" or "What does churn look like for new customers?" -- the agent extracts the cause, time horizon, and segment from your question instead of always returning the whole-dataset summary.

Held-out evaluation

Real train/test split, evaluated per cause -- not training-set performance. Baseline is a constant risk score for every customer, and should land at ~0.5 by construction: it's the floor every real model should clear.

Data validation

Runs automatically before any model touches the data (see backend/data_validation.py) -- this tab just lets you see the report.

Predict a customer

Fills unset fields with population defaults and applies the population-fitted Random Survival Forest (and cause-specific Cox, if a cause is selected) to the resulting profile. This is one constructed representative profile, not a real individual customer -- see which fields were stated vs. filled in the result.

Descriptive analytics

Schema-agnostic: every column is classified as numeric or categorical from its actual data type, not a hardcoded list -- this keeps working if the dataset is swapped for a different one following the same format (a CSV at data/telco.csv).

Backend must be running separately: uvicorn backend.main:app --reload (default: http://127.0.0.1:8000). See frontend/config.js to point at a deployed backend.
